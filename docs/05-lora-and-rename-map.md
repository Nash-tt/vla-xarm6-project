# 05 · 两处静默失败：LoRA 加载与 rename_map

> 代码：`pi0_ultrasound_lora/serve.py`

二者均属同一类缺陷：**不产生任何报错。**

---

## A. `from_pretrained` 对 LoRA checkpoint 静默返回随机权重

### 现象

训练已完成且 checkpoint 已保存。使用 `serve.py` 加载时**不抛出任何异常**，
但策略输出的动作无效，与训练时的 loss 不相符。

### 原因

本项目采用 LoRA 微调（PEFT），保存出的
`checkpoints/012250/pretrained_model/` 目录中**仅含 `adapter_model.safetensors`**，
不含完整的 `model.safetensors`。

而 `PI0Policy.from_pretrained(<该目录>)` 的加载路径**未覆盖 PEFT 分支**：
在未找到其预期的文件后，它按配置**构造并返回了一个模型**，
其中权重为随机初始化。既不抛出异常，也不输出警告。

此类缺陷的排查难度在于：调用成功、返回了模型、类型亦正确，
**唯一的问题是其中的数值是随机的。**

### 处理：`load_policy_checked`

`serve.py` 中的 `load_policy_checked` 复刻了官方
`lerobot/common/policies/factory.py:565` 的 PEFT 分支，走正确的适配器加载路径。

### 附加的主动校验

仅复刻分支仍不充分——若上游日后改变行为，同样会静默地得到随机权重。
因此加载后**主动校验所有 `lora_B` 的范数**：

```python
# LoRA 初始化时 A 随机、B 全零，故 B 的范数为零仅对应「未训练」情形。
# 适配器被正确加载后，B 必然已被训练出非零值。
if 所有 lora_B 的范数均为 0:
    硬失败
```

**全零即表示适配器未被加载。** 相较于让随机策略运行在真机上，直接终止是更好的选择。

### 结论

1. **「无报错」不等同于「加载成功」。** `from_pretrained` 这一命名暗示其会加载权重，
   但其契约并不包含「加载失败必须报错」。涉及权重的加载，应在加载后**主动校验内容**，
   而非信赖返回值。
2. 校验量的选取应满足「初始状态即不通过」的条件。LoRA 的 B 矩阵初始化即为全零，
   因此「B 仍为全零」天然构成可靠的失败信号。
   **选取校验量时，需明确其在「成功」与「失败」两种情形下分别取值如何。**
3. 该缺陷值得提交上游，目前尚未提交。

## B. `rename_map` 覆盖：其作用位置在预处理之前

### 现象

客户端发来的观测键名与策略期望的不一致（例如客户端使用 `camera`，
策略要求 `observation.images.rgb`）。意图通过 `rename_map` 完成映射，
但报错为找不到键——**映射似乎未生效**。

### 原因

`lerobot/async_inference/helpers.py:166` 在**预处理之前**即以客户端提供的键
索引策略的图像特征：

```python
policy_image_features[key]     # key 来自客户端观测，此时 rename_map 尚未作用
```

即：**传入的键名必须是「策略自身的键名」**，`rename_map` 在该位置无法生效。

（`remote/README.md` 中已将这一点列为硬性要求：
客户端的 camera key 必须直接使用策略的键名。）

### 处理

`serve.py` 原实现会**无条件**以客户端的 `rename_map` 覆盖服务端配置。
现改为：**仅当客户端显式发送 `rename_map` 时才覆盖**，
未发送则保留服务端配置。

### 结论

实现重命名/映射类功能时，其**作用位置比直觉更靠后**：
在数据管线中，映射通常只覆盖「送入模型之前」的一小段，
而管线中更早的「以键名查表」步骤（定位相机特征、查询 stats、拼接 batch）
均已按原键名执行完毕。
**排查映射不生效时，应先定位管线中最早使用键名的位置。**
