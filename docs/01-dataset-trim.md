# 01 · 数据集裁剪：接近段的识别与裁除

> 工具：`tools/trim_scan_segments.py`　校验：`tools/verify_trim.py`

## 现象

真机运行时，机械臂启动后立即向远离患者的方向运动。离线检查示范数据的 `action` 曲线，
发现每条轨迹前 40% 以上的区段内动作近似为常量：此时探头仍位于数百毫米之外，
而 `action` 冻结在某个远端目标点上。

## 原因

每条轨迹在时序上由两段构成：

| 段 | 占比 | `action` 语义 |
|---|---|---|
| 接近段 | ~44% | 常量，指向数百毫米外的目标点 |
| 扫描段 | ~56% | 有意义的扫描运动，`action ≈ state + 0.2mm` |

仅扫描段具备任务语义。接近段等价于要求模型在任意观测下输出该远端常量，
而模型确实习得了这一先验，因此在真机上表现为向远端跳变。

该问题的隐蔽之处在于：其表征与模型或训练问题一致（loss 正常下降、曲线平滑），
实际成因却是数据中有 44% 的样本在提供错误的监督信号。

## 判据：窗口密度

初版采用「自后向前定位首个动作衰减点、保留其后 95%」的规则，该判据不成立：
它会在保留区起始处残留约 50 帧的衰减尾巴，裁剪后 `|action − state|` 的 p99 仍达
**28mm**，说明接近段的尾部仍在提供「跳向远端」的监督。

改为**窗口密度**判据：

- 以 `win = 1s`（15 帧）为窗口滑动
- 统计窗口内 `|action − state| < tol = 0.2`（mm）的比例
- 取满足密度阈值的最后一段连续区间

由此得到的边界处，`|action − state|` 才真正收敛。

## 实现：仅修改元数据，不重编码视频

裁剪不修改 mp4，仅重写 parquet 与元数据：

- `timestamp`——重写为自 0 开始的回合内相对时间
- `frame_index`、`index`——全局重排
- 每回合的 `from_timestamp`——记录该回合在原始视频中的起始偏移

依据是 LeRobot 的取帧路径使用 **`from_timestamp + timestamp`**
（`decode_video_frames_pyav`）：只要这两个量一致，即可还原原视频中的对应区段。

**验证**：抽取 168 帧逐像素比对裁剪前后，**168/168 完全一致**。

## 结果

```
49053 帧  →  27312 帧   （55.7%）
28 个回合（不变）
边界中位帧号 761
```

## 裁剪后的必要步骤

裁剪版**不具备可用的 `meta/stats.json`**，不重算则训练无法启动。
该步骤存在一处必须注意的约束（必须指定 `--donor`），详见[文档 02](02-stats-json.md)。

```bash
python tools/trim_scan_segments.py --src <原数据集> --dst <裁剪版>
python tools/recompute_stats_local.py --root <裁剪版> --donor <原数据集>   # --donor 不可省略
python tools/verify_trim.py --src <原数据集> --dst <裁剪版>
```

## 上游数据中的一处缺陷

源数据集 `meta/episodes/*.parquet` 中的**逐回合 `stats/*` 列为陈旧值**：
28 个回合中有 18 个的 roll 统计仍为角度展开（unwrap）之前的值。

该缺陷**不影响训练**，因为读取路径不消费这些列（训练读取的是数据集级的
`meta/stats.json`）。但若后续需要使用逐回合统计，须先知晓其不可靠。

## 结论

1. 数据集的缺陷会以模型问题或训练问题的形式表现出来。真机行为异常时，
   优先绘制并检查示范数据，其效率高于参数调整。
2. 判据应按「目标切除对象」设计，并以**下游量**验证。初版后缀规则在自身指标上
   表现合理，却残留了提供错误监督的区段；应以 `|action − state|` 的 p99 等下游指标
   检验判据，而非以判据自身的定义自证。
3. 仅修改元数据、不重编码，是此类裁剪的合适做法：速度快、占用低，
   且可逐像素证明无损。
