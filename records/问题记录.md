## 1. 数据标签与统计量的排查过程

### P-01 / P-02：先核查标签，再调整模型

**现象。** 历史数据包含接近段，目标动作在长时间内保持不变，而实际末端仍在接近。角度跨越 ±180° 时，数值跳变还会将 roll 标准差放大。

**定位。** 比较同一时刻的实际状态与生效指令，分别计算平移距离和周期姿态差；同时检查动作序列是否冻结、异常是否集中于轨迹开头。对角度应比较展开前后的分布，而不把数值跳变误判为真实旋转。

**处理。** 现有工具结合时间窗口内异常密度、后续有效比例和大位置偏差的结束点识别裁剪边界；逐回合 unwrap roll 后统一分支，并重算统计量。

**验证与边界。** 历史数量与分布结果见上表，本次核对实现但没有重跑。孤立异常只报告时可能仍保留在数据中；触发裁剪上限的回合需人工审查。裁去接近段意味着训练任务聚焦扫描，不能据此认定模型具备从任意远处接近工件的能力。

### P-03：统计文件完整性与数值精度

**现象。** 训练在读取图像统计时出现 `KeyError`。历史还记录一维标准差重算差异约 3.5%。

**原因。** 图像统计缺键与数值精度是两个不同问题。前者来自重算程序只生成部分特征；后者与 float32 中 `E[x²] − E[x]²` 的消减误差有关，均值较大、方差较小时更明显。

**处理。** 缺键通过 donor 条目补充、数值统计重算及完整性断言处理。精度问题应使用 float64 参考计算核对，明确是否需要改变统计实现，不能以完整性通过代替数值精度验证。

**历史证据限制。** 旧记录给出 std 0.390023 与 float64 参考 0.376698，却将对应维度称为 gripper。本项目六维 TCP 定义没有夹爪维度，该命名有误；数值所属数据版本与维度应重新核对。本次不将它当作当前六维数据的已确认精度结果，也没有改写统计算法。

### P-04：解码容差不等于同步误差

**定位思路。** 长拼接视频中的 float32 时间格点随时间增大，某些时间比较会超过默认容差。应先对照请求帧、解码帧和最近时间选择，而不是直接判定采集同步失败。

**现有处理。** 各训练脚本显式设置 `tolerance_s=1e-3`。历史记录为原数据少量帧超过 1e-4 s，裁剪版未超出。

**边界。** 容差是解码校验阈值；采集对齐阈值为另一层的毫秒级规则。两者不能混用，放宽解码容差也不能证明图像与机器人真实物理时刻已经精确一致。

## 2. 模型加载与异步链路

### P-05 / P-06：检查权重内容与图像入口

**历史现象。** 普通加载函数返回模型却未正确处理 LoRA 产物；图像键映射在部分前置访问后才执行，或被空配置覆盖。

**当前处理。** `load_policy_checked()` 分别加载底座和适配器，检查 `lora_B` 存在及非全零；`SendPolicyInstructions()` 在客户端未指定映射时保留 checkpoint 配置。π0 发送侧使用相机槽位名称。

**验证边界。** 适配器非零只能排除部分失败模式；还应核对底座 revision 和离线输出。`serve.py --ckpt` 存在性检查不是模型加载验证，实际加载在策略指令 RPC 内发生。其他模型的特征推导不同，不能把 π0 规则作为通用修复。

### P-07 / P-08：动作断供与版本分叉

**定位顺序。** 先检查接收线程 traceback 和 `rx_error`，再检查发送错误及服务端是否过滤观测，最后检查队列时间步覆盖。接收线程方法缺失、网络失败和观测过滤都会表现为队列没有新动作，但处理方法不同。

**当前处理。** 兼容对象自检调用实际所需方法；发送移入独立线程；错误传至主循环。空队列需要新预测时使用 `must_go`，但该字段是跳过检查的请求标志，不能当作周期保活。

**版本维护。** 仓库传输层统一为 `remote/remote_client.py`，真机客户端继承该实现。proto 文件仍在两个代码目录各存一份，部署时应一起核对。工控机旧测试目录是否已替换，本次没有远程验证。

## 3. 环境与队列问题

### P-09：依赖污染及视频后端

历史安装另一框架时，依赖写入了激活的 LeRobot 环境，影响 torch、transformers 与训练框架。当前脚本通过显式训练入口减少对 shell 激活状态的依赖；安装操作仍应指定目标解释器。

历史 torchcodec 报 `LIBFFI_BASE_7.0` 相关符号错误。当前项目视频入口采用 PyAV，属于绕开故障路径，不是修复 torchcodec。首次换环境需运行数据读取和小步训练验证，不能仅由安装命令成功确认兼容。

历史 SmolVLM processor 缺少 `num2words`，补装依赖后继续运行；是否由环境污染造成只属历史推测。代理 scheme 与交互式 shell 启动脚本中的阻塞输入也影响过启动，均需结合实际错误定位，不应随意改动全局环境。

### P-10：等待程序误识别自身

历史队列用 `pgrep -f` 按命令行字符串判断训练进程存活，监控程序自身也包含该字符串，导致训练结束后仍等待。完成日志与 GPU 无实际训练占用构成关键排查证据。

历史处理改用包含训练入口的更具体条件，并在启动后检查进程与非空日志。本次未核对仓库外脚本是否保持该修复。以后由启动程序保存 PID、等待退出状态，并确认完成产物，比仅依据字符串存在更可追溯。

### P-12：其他训练框架读取数据时出现误导性网络错误

历史评估的 openpi 环境固定了较旧 LeRobot，读取 v3 数据时预期的 tasks、episodes 文件布局不符。缺失文件被上层捕获后触发 Hub 获取，最终显示离线或网络错误，掩盖了格式原因。

应分别检查数据版本、元数据布局和底层读取函数，再检查联网配置。旧评估还指出网络协议与归一化需要适配；它属于当时本机版本的兼容性记录，不是当前 openpi 的通用结论。本次没有切换框架或重新验证外部实现，不保留旧文档中未证实的固定工期判断。

## 4. 本次文档核对发现的待验证问题

### P-13：训练与部署角度表示不同

**代码证据。** 训练工具逐回合展开 roll；真机 `get_observation()` 直接取控制器上报位姿。限速器处理目标角度的周期差并折返，默认直接路径不做同样变换。

**状态。** 已确认实现差异，尚未证明其实际影响。需要用同一观测比较归一化结果和策略输出，再决定在部署侧统一分支或调整数据表示；本次没有修改控制代码。

### P-14：训练完成与部署接入被混淆

**代码证据。** 轻量客户端在策略握手中硬编码 `policy_type="pi0"`，真机客户端继承该入口。SmolVLA 和 ACT 的独立训练完成日志不能证明它们已接入此链路。

**状态。** 文档已明确边界。接入新模型前需修改并测试类型、特征、后处理与动作队列，记录独立回放及影子结果。

## 5. 工控机帧率总结补充（2026-10-13整合）

以下数值来自2026-10-11实验的工控机总结，本次没有重新计算原始日志。来源SHA-256、各阶段数据和缺失配置见 [部署实验](部署实验.md)。

### P-15：慢观测上传阻塞动作时钟，解耦后仍断供

**现象。** 早期300步回放耗时120秒，约2.50 Hz；发送独立后为46.2秒、6.50 Hz。解耦后RPC平均3.39秒、最大10.70秒，块到达间隔平均3.64秒，超过50步在15 Hz下的3.33秒完整覆盖。

**定位证据。** 报告中88次推理中位0.370秒、最大0.917秒；同大小观测在另一客户端上传明显更快。该对照支持当时工控机上行是主要瓶颈。“TCP丢包指数退避”与离散延迟台阶相符，但仍是原因推断，本次无抓包证据。

**处理。** 当前仓库已将发送RPC、动作消费与接收分线程，限制待发观测、预装首块、提前预取并启用真机gzip。上传中拒绝新请求，不是不断覆盖待发观测。gzip与预取不能消除底层长尾。

**验证状态。** 报告70秒真机约13.91 Hz，仍有6次大于0.5秒间隙，最大1.47秒。属于部分改善，尚未解决稳定15 Hz。`50/3.64≈13.7 Hz` 仅是忽略预测重叠、请求策略和长尾的粗略供给估算，不是严格的系统吞吐上界。

**后续。** 按固定载荷和网络路径做对照，补充分段耗时、队列深度、块步号与空闲时间，逐次定位间隙。跨机器时间差需要时钟校准。

### P-16：模型绝对目标跳变影响首次真机接入

**现象。** 报告70秒原始相邻目标最大平移跳变27.614 mm，219次大于3 mm；直接下发不符合当前单步检查。

**处理。** 可选 `PolicyTargetRateLimiter` 以上一命令为基点，每处理一个动作仅推进 `速度/fps` 的最大步长。7和10 mm/s在15 Hz下分别对应0.4667和0.6667 mm/步，姿态限速为RPY周期差向量范数约束。

**验证与限制。** 两次报告有界真机运行SDK返回0，跟踪误差未触及当前阈值；70秒平移限速参与约96.9%的动作。说明限速命令可执行，不证明原始目标、示范复现或超声扫描任务正确。队列空时限速器不继续推进，累计运动仍由运行时长等外层条件约束。

### P-17：超声数据超龄与结束阶段通道关闭

**超声事件。** 报告包年龄0.551秒触发0.5秒限制。重启PhaseLink并开始扫查后，诊断约38.4包/s、最大年龄0.105秒。数据流恢复得到报告支持，但此前停顿根因未确认，不能将“重启有效”当作根因分析完成。

**通道事件。** 报告正常结束后偶发 `Channel closed`。仓库实现先调用 `client.stop()` 关闭通道，再等待线程退出，存在与仍在上传的线程交叉的可能。调整退出顺序是待实施方案；运行中同类错误仍视为错误，不能统一当作收尾噪声忽略。
