# 04 · 时间戳精度：被 float32 抵消的容差

## 现象

数据集本身无误，但读取视频时偶发解码失败，报错为「找不到落在该时间戳上的帧」。
关键特征是：**仅在长时间戳上失败，短回合完全正常**。

## 原因

LeRobot 的 `decode_video_frames_pyav` 中存在如下语句：

```python
timestamps = torch.tensor(timestamps)      # float64 → float32
```

`timestamps` 本身由 float64 计算得出，进入 `torch.tensor` 时被**降级为 float32**。
float32 在 t≈1277s 处的 ULP（最小可分辨间隔）为：

| 时间戳 | float32 ULP | 默认 `tolerance_s = 1e-4` |
|---|---|---|
| 1277 s | 1.22e-4 | **已超出** |
| 3270 s | 2.44e-4 | 超出 2.4 倍 |

即：数据集时长越长、时间戳越靠后，float32 能表示的间隔越粗。
当 ULP 超过解码器用于匹配帧的容差时，匹配即失败。

该缺陷的严重程度**随数据集时长递增**，因此在短测试集上不会复现。

## 处理

训练与推理时将容差放宽至 1e-3：

```bash
--tolerance_s=1e-3
```

该参数已在 `run_train_smolvla_scan.sh` 中固定，并附有上述依据。

在 15 FPS 下，1e-3 对应 66.7ms 的帧间隔，远大于任何真实的时间戳抖动，
同时远小于单帧时长，因此**不会造成错帧匹配**，仅避免比较被 float32 的表示精度所限。

## 结论

1. 仅在「长数据」上出现的缺陷，在短验证集上无法被检出。
   **验证集需覆盖真实数据的时长范围**，否则「本地已跑通」不构成有效保证。
2. 对 `torch.tensor(python_float)` 这类写法应保持警觉：
   torch 默认浮点 dtype 为 float32，而 numpy/Python 侧通常为 float64。
   此类静默降级在数值敏感处（时间戳、角度、坐标）均会引发问题。
3. 处理方式应优先选择「放宽容差」，而非「修改上游 dtype」：
   后者需改动库代码，且会使本地行为偏离官方，导致后续无法对账。
