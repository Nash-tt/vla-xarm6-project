# 01 · 数据集裁剪：把「接近段」删掉

> 工具：`tools/trim_scan_segments.py`　校验：`tools/verify_trim.py`

## 现象

真机上跑策略时，机械臂一开机就往远离患者的方向窜出去。
回头离线看示范数据的 `action` 曲线，发现**每条轨迹的前 40% 多，动作几乎是一条水平线**——
探头还停在几百毫米外，`action` 冻在某个远处的目标点上不动。

## 根因

每条轨迹在时序上是两段拼接的：

| 段 | 占比 | `action` 的语义 |
|---|---|---|
| 接近段 | ~44% | 常量，指向一个几百 mm 外的目标点 |
| 扫描段 | ~56% | 有意义的扫描运动，`action ≈ state + 0.2mm` |

只有扫描段是任务语义。接近段等于在教模型「不管画面里是什么，都输出那个远处的点」。
模型确实学到了——它把这个常量当成了先验，于是真机一开始就往外跳。

**这类问题的危险之处在于：它看起来像模型问题或训练问题**（loss 正常下降、曲线平滑），
实际上数据里就有 44% 的样本在教错误的东西。

## 判据：窗口密度，不是「后缀规则」

第一版用的是「从后往前找第一个动作衰减点，保留其后 95%」的思路，
**结果是错的**：它会在保留区开头留下一段约 50 帧的衰减尾巴，
裁完之后 `|action - state|` 的 p99 还有 **28mm**——说明接近段的尾巴还在教「跳到远处」。

改成**窗口密度**判据：

- 以 `win = 1s`（15 帧）为窗口滑动
- 计算窗口内 `|action - state|` 小于 `tol = 0.2`（mm）的比例
- 取满足密度阈值的最后一段连续区间

这样切出来的边界，`|action - state|` 是真正干净的。

## 实现：只改元数据，不重编码视频

裁剪**不碰 mp4**，只改 parquet 与元数据：

- `timestamp`——重写为从 0 开始的回合内相对时间
- `frame_index`、`index`——全局重排
- 每回合的 `from_timestamp`——记住该回合在原始视频里的起始偏移

之所以敢这么做，是因为 LeRobot 的读取路径取帧用的是
**`from_timestamp + timestamp`**（`decode_video_frames_pyav`），
只要这两个量对得上，读出来的就是原视频里那段。

**验证**：抽 168 帧逐像素比对裁剪前后，**168/168 完全一致**。

## 结果

```
49053 帧  →  27312 帧   (55.7%)
28 个回合（不变）
边界中位帧号 761
```

## 裁剪之后必须做的一件事

裁剪版**没有可用的 `meta/stats.json`**，不重算的话训练起不来。
这一步有个坑（必须带 `--donor`），单独写在 [文档 02](02-stats-json.md) 里。

```bash
python tools/trim_scan_segments.py --src <原数据集> --dst <裁剪版>
python tools/recompute_stats_local.py --root <裁剪版> --donor <原数据集>   # --donor 不能省
python tools/verify_trim.py --src <原数据集> --dst <裁剪版>
```

## 顺带发现的一个上游数据缺陷

源数据集 `meta/episodes/*.parquet` 里的**逐回合 `stats/*` 列是陈旧的**：
28 个回合里有 18 个的 roll 统计仍然是角度展开（unwrap）之前的值。

这一条**不影响训练**，因为读取路径并不消费这些列（训练读的是数据集级的
`meta/stats.json`）。但如果你哪天想用逐回合统计做点什么，得先知道它们是坏的。

## 教训

1. 数据集的毛病会伪装成模型的毛病。真机行为异常时，先把示范数据画出来看一眼，
   比调参快得多。
2. 判据要按「真正想切掉什么」设计。我第一版的后缀规则在指标上看着合理，
   却留下一段正在教错误动作的尾巴——**要用下游量（`|action-state|` p99）来验证判据，
   而不是用判据自己的定义来验证自己**。
3. 只改元数据不重编码，是这类裁剪的正确姿势：快、省空间、且可逐像素证明无损。
