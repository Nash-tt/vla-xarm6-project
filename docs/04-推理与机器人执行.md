# 推理服务、传输与机器人执行

核对日期：2026-10-13。实现说明已按 `2b3522f` 复核，并整合工控机帧率总结；实验数值与来源见 [部署实验](../records/部署实验.md)。

## 1. 推理服务与网络传输

GPU 侧 `pi0_ultrasound_lora/serve.py` 继承 LeRobot 策略服务，主要补充两项行为：

- 检测 LoRA checkpoint，先加载原始底座，再使用 PEFT 加载适配器；检查模型中是否存在 `lora_B` 参数及是否全部为零。
- 客户端没有提供 `rename_map` 时，保留 checkpoint 中的映射配置，避免被空配置覆盖。

`lora_B` 非零检查能够发现缺失或未更新的适配器，但不能单独证明底座、版本和全部权重均正确，仍需记录底座 revision 并进行推理对照。

模型在客户端调用 `SendPolicyInstructions` 后加载。`serve.py --ckpt` 启动时仅检查路径存在，真正加载使用客户端策略指令中的路径；因此服务端启动日志和端口可连接不能证明权重已成功加载。

工控机传输层为 `pi0_ultrasound_lora/remote/remote_client.py`。它通过 gRPC 发送带时间和步号的观测，接收动作块。两个生成的 proto 文件和传输对象定义需与服务端兼容。发送线程、接收线程及动作队列分别管理观测请求、网络接收和执行。客户端通过 `--policy-type pi0/act/smolvla` 选择策略类型。服务端检查 checkpoint 类型、权重文件、相机键、动作块范围及 ACT/SmolVLA 的六维输出；类型或特征不匹配时拒绝加载。

π0 默认在发送侧将两路图像缩为 224×224。ACT/SmolVLA 真机入口默认发送 RGB 1280×720、超声 256×256，以保持已保存训练特征的尺寸与宽高比；可通过各图像尺寸参数覆盖。发送原生图像会增加上传体积，必须重新测量网络延迟，不能沿用 π0 小图路径的结果。gzip 为可选压缩。服务端的 `--wire numpy/torch` 控制下行动作的数据类型，不控制上行图像尺寸。

当需要强制新观测入队时，客户端设置 `must_go`；服务端据此跳过相关合理性检查。它不是周期心跳。重叠动作按 `latest_only` 处理，同一时间步采用新块中的结果，已执行的旧时间步被过滤。当前未进行时间集成，即没有将多个预测按权重合成为单个动作。

## 2. 真机客户端与执行约束

`robot/real_robot/real_robot_client.py` 继承传输客户端，增加 RealSense、实时超声和 xArm 状态读取，以及动作检查和运动接口。默认影子模式仅记录策略输出；运动执行需要显式执行参数与确认字符串。`--validate-only` 用于本地依赖和配置检查，不连接设备。

`--preview-rgb` 可显示实时 RGB，相机采集线程将现有原生彩色帧交给独立显示进程，容量 1 的非阻塞队列与刷新限频限制显示积压。显示端只做颜色转换和显示缩放，不改动模型输入。关闭预览窗口或按 Esc/q 会请求结束测试；控制循环和初始动作等待检查该事件，同步模型加载仍需返回后才处理，不能视为即时硬件停止。工控机需从桌面会话启动 GUI，详见操作指南。

每次下发前检查连接、控制器错误与警告、状态、力与力矩、跟踪误差及动作跳变。示教轨迹约束仅在提供 `--safety-trajectory` 时生效。可选速率限制器将远处目标变为逐步逼近的位姿；默认不开启。

| 检查项 | 当前默认值 | 适用范围 |
|---|---|---|
| 力 / 力矩上限 | 40 N / 5 Nm | 每次下发前检查 |
| 单步位置 / 姿态变化 | 3 mm / 2° | 相邻目标 |
| 跟踪误差 | 25 mm / 5° | 目标与实际 TCP；2026-10-13 按用户要求由 12 mm 调整 |
| 轨迹管 | 15 mm / 8° | 必须提供安全轨迹 |
| 图像最大年龄 | 0.5 s | RealSense 与超声 |
| xArm 状态最大年龄 | 0.25 s | `snapshot()` 默认值，不受图像参数控制 |
| 单次运行时间 | 10 s | 控制循环 |
| 动作队列空超时 | 0，关闭 | 需显式配置才能启用 |

这些数值是代码默认配置，不代表已完成接触扫描场景的安全验证。空队列时程序不重放旧动作，但网络连接存活、发送接收均未报错时，仍可能长期没有新动作，因此不能把空队列超时关闭解释为不存在停供风险。

## 3. 启动与控制时序

客户端依次建立通道、发送策略配置、启动接收及发送线程、请求初始观测，等待第一组动作后开始固定频率执行。回放入口默认额外预热两个动作块；真机入口的初始等待时间默认 180 s，与回放入口 120 s 不同。

观测发送采用容量为 1 的队列。`observation_pending` 在排队和上传期间置位，新请求在该期间被拒绝；它不会不断用最新图像覆盖已排队的旧观测。发送线程执行 RPC，控制循环继续按固定频率消费动作。动作队列量不高于 `chunk-size-threshold` 比例时允许请求补充，默认阈值 0.9。阈值影响请求时机，不是运动安全阈值。

发送和接收线程的错误写入 `observation_error` 与 `rx_error`，主循环据此退出。gRPC 通道本身配置了部分错误的重试；最终传播到主循环的错误不会由控制逻辑无限重试。

控制环使用单调时钟计算下一期限，运行落后时重置期限，避免持续追赶。Python 线程调度、网络和设备回调都可能产生抖动，实际执行频率需要测量。

### 3.1 四种频率与缓冲预算

RealSense采集默认30 FPS；超声包速率由设备和写盘过程决定；观测请求由队列水位触发；动作消费目标为15 Hz。它们各有含义，不能把观测次数直接当作机器人动作频率。

50步动作在15 Hz下覆盖3.33 s。请求新块时的实际剩余缓冲为 `队列剩余动作数 / 15`，不是始终3.33 s；水位0.9、完整块50步时，约剩45步，即3.0 s。重叠预测与步号过滤也会影响有效新动作数量。因此需要比较从请求到有效动作入队的延迟长尾与当时实际缓冲，不能只看平均RPC延迟。

初始动作预装避免加载期间启动空队列，但不解决运行中补充过慢。gzip属于无损传输压缩，当前图像仍以数组传输；拟议JPEG/WebP编码需要两端协议及输入回归验证，尚未实现。

### 3.2 动作间隙和断供行为

动作队列为空时不下发新目标，不重放旧动作，也没有持续生成本地插值步骤。程序没有因空队列主动执行停车，不能由此推断控制器或接触状态一定保持安全。`queue-empty-stop=0` 是工控机报告中的实验条件；任务允许停顿、停车及恢复条件仍需专门验证。

## 4. 原始目标、限速命令与执行日志

日志分别保存模型原始目标 `raw_policy_target`、接受检查的目标 `commanded_tcp_pose`，以及 `rate_limit` 结果。默认路径两者相同；开启限速后，本机逐步逼近远处绝对目标，平移与姿态分别按速度上限计算每周期步长。限速路径会折返角度；默认直接目标路径没有统一角度折返。

### 4.1 限速器的具体计算

首次命令以实际位姿为基点，后续以上一条限速命令为基点。平移差向量按范数限制至 `linear_speed / fps`；姿态按各RPY分量的周期最短差计算，并限制向量范数至 `angular_speed / fps`。此处是RPY参数空间的速率约束，不等同于一般三维旋转的严格角速度范数。

15 Hz时，7 mm/s对应0.4667 mm/步，10 mm/s对应0.6667 mm/步，1 deg/s对应0.0667°/步。这是命令步长上限，不保证实际机器人每秒一定走完相同距离。队列空时不推进限速器；恢复时也不按空闲墙钟时间补走大步。

注意这里的速度约束来自本地限速器对位置命令的计算，不是 `set_servo_cartesian` 的 speed 参数。部署 SDK 将 speed、mvacc、mvtime 标为 reserved；[厂商伺服指南](https://docs.supportarticle.ufactory.cc/support_articles/developer/ufactory-servo-mode-guide.html) 也说明这些参数当前无效，并建议平滑插值、50–200 Hz 下发、单步距离不超过 10 mm。10 mm 为通用接口使用建议，不能当作本项目接触扫描的已验证安全值。当前 15 Hz 策略消费与高频伺服发送应分别设计，本地高频插值尚未实现。扫描标签的相邻位置距离 P99 约 1.4 mm、最大约 5 mm，仅 4 对超过 3 mm，实际核对见 D-20。

限速改变策略的时间尺度，模型目标可能在尚未到达时再次改变方向。跟踪误差较小只能说明机器人跟踪限速命令的结果，不能代替模型与示范轨迹的误差。工控机70秒报告中平移限速参与944/974步，详细条件与限制见部署实验。

影子模式记录 `shadow_valid` 与拒绝原因，主要验证几何约束；执行模式才要求力信号有效并进行对应检查。影子测试通过不代表全部执行条件通过，特别是力信号、起始位姿和 SDK 运动返回码。

实际入口先取待执行首目标，按初始实际位姿检查距离和单步变化；首步不合格时在运动使能前退出，并记录 `execute_request`/`execute_setup`。限速模式的预检使用临时限速器，不改变正式执行历史。通过预检后的执行准备会改变使能、模式和状态，但没有自动移动到扫描起点。异常或中断在已执行状态下进入停止状态，不自动清除错误。实际停止与恢复步骤应按设备测试记录核实。

## 5. 验证次序

先验证 checkpoint 的加载与离线输出，再使用数据回放检查网络对象、时序和误差，最后接入实时观测开展影子测试。只有完成相应设备与影子检查后，才安排有界运动实验。本次文档重建没有执行运动测试。

完整操作和验证命令见 [环境与操作指南](06-环境与操作指南.md)。每次部署记录服务端和客户端 commit、checkpoint、图像处理、超声配置、队列参数及日志位置。

工控机报告已提供10秒和70秒执行结果，但仍有长动作间隙，尚未证明稳定无断供的15 Hz或完整扫查成功。正常结束阶段的 `Channel closed` 可能来自通道先关闭、线程尚未退出；当前代码确实先 `client.stop()` 再 join。该解释尚未由本次日志独立验证，运行中同类错误仍须按传输故障处理。

2026-10-14 E-06 相对模型执行验证（D-22）首步约 1.016mm，通过 3mm 限制，50 条 servo 指令成功后因动作队列空置 3.063 秒停止。该证据表明相对输出可以还原并执行第一段轨迹，但不表明异步传输已满足连续控制；详见部署实验记录。

### 允许断供停顿的测试模式（2026-10-14）

用户允许先停顿执行、之后优化延迟时，可设置 `--queue-empty-stop 0`，队列空置不因等待时长退出。空队列不重复旧命令，机器人执行完最后目标后等待；恢复时沿用原几何检查，不自动跨越跳变。等待期间仍检查机器人状态、力与力矩，网络线程错误、窗口退出和其他异常仍会结束测试。`queue_pause`/`queue_resume` 记录空队列及恢复时长。

`--duration-clock wall` 为默认，max-seconds 按控制循环墙钟时间计算。新增 `--duration-clock actions` 按已成功处理的动作数量 / fps 计算，空等待不计入。这是动作时间预算，不是实测机械臂移动时长，重复位置目标同样计数。50 秒/15Hz 对应 750 个动作。队列永远不补充时没有动作预算上的截止时间，桌面测试调度任务另有 20 分钟外层时限；该调度时限不是已验证的机器人停车机制，应主动监控并通过客户端退出处理异常。此模式没有完成整条示教路径的结束判定。

D-24 准备阶段按用户要求选择现有本地目标限速器作为段间平滑尝试，计划 2mm/s、1degree/s；这仍为 15Hz 下的逐命令限速，不是高频插值或 RTC。限速检查作用于最终命令，原始目标可能偏差更大，应结合 raw_policy_target 与 rate_limit 分析，不将命令合格当作模型预测合格。当前执行状态见部署实验。

D-24 已完成750动作/50秒名义预算，首末下发148.471秒含25次停顿；2mm/s限速作用于全部750条命令，原始目标最大距实际37.225mm。该结果证明有停顿的预算执行与恢复，不能证明原模型直接轨迹或超声任务成功。本次单独图像年龄参数为1秒，代码默认仍0.5秒。

### 观测与模型动作导出

`tools/summarize_live_policy.py --log <JSONL> --output-dir <REPORT_DIR>` 将已有真机 JSONL 导出为观测、动作、停顿 CSV、汇总 Markdown/JSON 与交互式 HTML。CSV 保存全部六维模型输入 state、原始绝对 action、本地平滑命令与下发前反馈，以及位置距离；CSV 使用 UTF-8 BOM 方便表格软件读取。完整运行数据与报告保留在项目外，仓库只保留有限汇总。

原始 action 是服务端反归一化及相对参考还原后的绝对目标，不是模型归一化空间或原始相对增量。当前日志没有观测 timestep、chunk 对应观测ID、完整接收段与被过滤动作，导出工具不能可靠配对生成观测和预测段，不能恢复全部推理输出。HTML 的观测与动作浏览相互独立；raw-minus-actual 使用下发前实际反馈，不能解释为 action 减生成观测 state。原始目标与实际 TCP 差包含预测未来距离和限速滞后，不等于示教标签预测误差；命令与实际反馈差也不是执行后的稳态跟踪误差。
