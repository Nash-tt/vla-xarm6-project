# 问题记录（`docs/`）

这里按**时间顺序**记录实施过程中踩过的坑，一篇一个具体问题，统一按
**现象 → 原因 → 处理 → 验证 → 结论** 组织。写的是**当时**的判断与实现。

> **这不是现行的实现说明。** 早期几篇描述的做法，有些后来已经改了；
> 想知道「代码现在长什么样、为什么这么设计」，看 [`../design/`](../design/README.md)。
> 两者冲突时**以 `design/` 与代码为准**；`docs/` 已核对出的偏差集中列在
> [`design/README.md` 第四节](../design/README.md#四和-docs-的关系)，引用本目录时请对照那张表。

## 十篇

| 编号 | 文档 | 问题 | 结论 / 留下的东西 |
|---|---|---|---|
| 01 | [数据集裁剪：接近段](01-dataset-trim.md) | 前约 44% 的轨迹在教模型「输出远端目标点」，而不是扫描 | 用**窗口密度**判据裁掉；只改元数据、不重编码，逐像素校验 168/168 一致 |
| 02 | [`meta/stats.json`](02-stats-json.md) | A. 重算统计量丢键 → 训练启动即 `KeyError`；B. float32 累加器把 `std` 抬高了 3.5% | 重算**必须带 `--donor`**；校验时别拿精确池化值当判据 |
| 03 | [roll 角度表示](03-roll-angle.md) | 同批轨迹的 wrap 版让 roll 的 `std` 从 7.77 涨到 172（**22 倍**） | 归一化是 `MEAN_STD`，尺度失真直接影响回归；两版现已统一为**展开口径** |
| 04 | [时间戳精度与 `tolerance_s`](04-timestamp-tolerance.md) | float32 在 t≈1277 s 处的 ULP（1.22e-4）**大于**默认容差 1e-4 | 传 `--tolerance_s=1e-3`。它只影响校验、不影响选帧，代价为零 |
| 05 | [LoRA 加载与 `rename_map`](05-lora-and-rename-map.md) | A. `from_pretrained` 对 LoRA checkpoint **静默**返回随机初始化；B. `rename_map` 的作用位置在预处理**之前** | 用适配器 B 矩阵的范数判断是否真的加载；键名必须在发送侧就写成 policy 键名 |
| 06 | [远程轻量客户端](06-remote-client.md) | 单帧 2.96 MB → 0.30 MB 从哪来；一处让观测**静默丢弃**的接收线程缺陷；以及真机接入尚缺的工作 | 省下体积的主因是**发送侧 224×224 预缩**，不是图像编码 |
| 07 | [环境与工具链](07-environment.md) | conda 环境污染、torchcodec 失效、代理 scheme、缺依赖、`~/.bashrc` 阻塞式 `read`，以及 `pgrep -f` 自匹配让训练队列静默等 12 小时 | 本篇技术含量最低、工时消耗最高；`pgrep -f` / `pkill -f` 的匹配串绝不出现在自己的命令行里 |
| 08 | [openpi 兼容性评估](08-openpi-compat.md) | 换框架时，现有客户端与服务端能复用多少 | 数据侧是**硬阻塞**（已实测）；服务端 openpi 不含 gRPC |
| 09 | [两端接口契约](09-interface-contract.md) | 数据格式、维序、相机键名映射、roll 口径、带宽预算、安全阈值 | **仓库里唯一一份跨机器契约**，两台机器共用；改动须按第六节清单同步 |
| 10 | [两台机器的协作方式](10-collaboration.md) | 代码怎么在 GPU 机器与工控机之间流动；入库前的消毒清单 | 提交前的机械检查、绝不入库的项、文档约定都在这篇 |

### 建议阅读顺序

- **只想知道数据是怎么来的** → 01 → 02 → 03 → 04
- **要复现训练** → 02（`--donor`）→ 03（roll 口径）→ 04（容差）
- **要把模型跑上机器** → 06 → 09
- **第一次接手这个仓库** → 先读 [根 README](../README.md)，再读本章 10 与
  [`design/README.md`](../design/README.md)

每篇的**逐行要点、涉及哪些代码文件、判据在哪**，在 `design/` 对应篇里也有一份
（两套文档按同一批问题、两种组织方式写）。

## 与 `design/` 的分工

| | `docs/` | `design/` |
|---|---|---|
| 回答 | 当初**为什么**这么改 | 现在**是怎么搭的** |
| 组织 | 按时间，一篇一个问题 | 按层次，一篇一个环节 |
| 时效 | 记录当时的状态，**不回改** | 跟随代码，**冲突时以它为准** |

`design/` 的索引见 [`../design/README.md`](../design/README.md)；
`docs/` 各篇的一段话摘要另见[根 README 第三节](../README.md#三文档索引)。
