# US-VLA 复现与训练资源

本文汇总 2026-10-16 至 17 日有关 π0/π0.5 微调、batch、训练预算与显存的讨论。目标是理解资源需求并形成可复核的实验判断；不包含主机连接、代理配置和下载进度等临时操作。实测配置与状态见 [训练实验 E-08](../records/训练实验.md)，机器可读证据见 [E-08.json](../records/training/E-08.json)。

## 1. 当前复现范围与官方数据

[US-VLA 官方代码](https://github.com/VMVLab/US-VLA) 基于 π0.5，增加 USFM 专用超声编码器与特征融合。本轮先使用作者发布的 [usvla/US](https://huggingface.co/datasets/usvla/US)：120 回合、29,665 帧、30 Hz、5 类任务；固定数据 revision 为 `afa73d512b7a980b55e84536b47ae08c059b0697`。这是公开数据范围，不是论文全部 320 回合实验。

实际数据的 state 为 12 维（位姿与力/力矩），action 为 6 维增量；与部分上游文字描述存在差异，应以实际 schema 与数据变换为准，不额外重复减 state。模型输入 state/action 填充到 32 维，预测动作块长度为 50；三路图像进入模型前处理为 224×224。公开训练使用全部 120 回合，没有独立验证划分，不能由训练 loss 宣称泛化或论文指标复现。

已完成资源校验、完整数据统计和输入检查。USFM 官方 checkpoint 的真实结构与原 JAX 实现不完全兼容，本地修正了权重根路径、共享相对位置偏置、LayerScale、独立 Q/V 偏置、LayerNorm epsilon 与 GELU 等，保留新增输出投影及 token 接口。186 个预训练张量、85,665,360 个参数元素覆盖检查通过；与固定版上游 PyTorch 编码器的 float32 token 特征对照，最大绝对误差约 5.96e-6。该对照不包括整个策略、bf16/GPU 数值或训练效果。因此应称为“带 USFM 兼容修正的公开数据复现”，不能称完全未修改的官方代码运行。

## 2. LoRA 配置名不等于只训练 LoRA

LoRA 是在原权重旁加入低秩可训练矩阵的微调方式。判断实际训练范围必须核对冻结过滤器和优化器状态，不能只看配置名。

## 3. 梯度检查点的作用与官方实现

梯度检查点（gradient checkpointing，也称 rematerialization）在反向传播中重新计算部分中间结果，减少需要同时保存的激活，代价是额外计算。它不减少模型权重和 Adam 状态。

官方 OpenPI 的 JAX/Flax 路径及本次代码中，语言主干与动作专家的 Transformer block 使用 `nn.remat`、`nothing_saveable`；SigLIP 构建时 `scan=True`，其 block 也使用 `nn.remat`。US-VLA 新增 USFM 与融合模块未显式包装同样的 remat。此结论针对已核对的实现，不能外推到所有 PyTorch 移植版。

代码依据：[Gemma](https://github.com/Physical-Intelligence/openpi/blob/main/src/openpi/models/gemma.py)、[模型构建](https://github.com/Physical-Intelligence/openpi/blob/main/src/openpi/models/pi0.py)、[SigLIP](https://github.com/Physical-Intelligence/openpi/blob/main/src/openpi/models/siglip.py)。实际运行源码哈希记录在 E-08 摘要；网页 main 分支后续可能更新。

## 4. 显存：固定成本、计算缓冲与保留空间

训练显存可分为权重、优化器、梯度及激活/工作区，以及框架保留空间。权重和优化器基本不随 batch 变化；输入、中间激活与部分工作区随 batch、图像尺寸、序列长度和算法变化。梯度形状由可训练参数决定，但在编译计算中可与其他临时数据复用空间。

两组独立进程使用相同数据和预训练权重，各执行 5 次完整优化更新。参数按真实张量大小统计，临时区来自 XLA 编译分析，实际峰值来自 GPU allocator 的 `peak_bytes_in_use`。单位为 GiB（2^30 字节）。

| 内存组成 | batch 8 | batch 16 |
|---|---:|---:|
| 冻结参数权重，bf16 | 5.470 | 5.470 |
| 可训练参数权重，float32 | 2.197 | 2.197 |
| Adam 状态 | 4.395 | 4.395 |
| 单份输入 batch | 0.014 | 0.027 |
| 其他常驻分配及对齐残差 | 0.174 | 0.200 |
| 单步临时区：梯度、中间结果和算子工作区 | 4.660 | 5.875 |
| **实际缓冲峰值** | **16.909** | **18.164** |
| **JAX 显存池容量** | **32.029** | **32.061** |
| 池容量减实际缓冲峰值 | 15.120 | 13.897 |

“其他常驻分配”是 allocator 常驻占用减已计数训练状态和输入后的残差，未逐项归属。“临时区”中的空间可重复使用，不能再叠加一份理论梯度显存；也不能把这个合计任意分摊成每层激活。常规设备快照会将 JIT 内部归到整个编译函数，故本次结合编译分析，没有声称完成逐层独占峰值归因。

权重按模块拆分为：语言/动作专家含 LoRA 5.656 GiB，SigLIP 1.545 GiB，USFM 含输出投影 0.325 GiB，融合 0.133 GiB，其他策略投影 0.008 GiB，总计 7.667 GiB。

batch 16 相对 batch 8 的真实峰值增加约 1.25 GiB，即约 7.4%。两组池都扩容到约 32 GiB，因此 nvidia-smi 中约 32.6 GiB 的读数近似相同；nvidia-smi 还计入 CUDA 上下文与池外分配。已关闭启动时预分配，但这不等于禁用缓存池。池容量与真实张量需求不能混淆。

本例固定权重和优化器就有约 12.06 GiB，且启用了梯度检查点，因此 batch 8→16 的显存增幅不大。不能推广为“梯度检查点下 batch 对显存影响都不大”，也不能线性推算 batch 32；分辨率、序列和算子策略改变时应重新测量。

参考：[JAX 显存分配](https://docs.jax.dev/en/latest/gpu_memory_allocation.html)、[设备内存剖析](https://docs.jax.dev/en/latest/device_memory_profiling.html)。

## 5. batch、step 与训练预算怎么确定

有效 batch＝每卡实际 batch × GPU 数 × 梯度累积次数。step 在这里指一次优化器更新，epoch 指名义上完整遍历训练集一次。

`更新步数 ≈ 训练样本数 × epoch 数 ÷ 有效 batch`

| 当前 29,665 帧数据 | 总更新步数 | 累计样本数 | 名义 epoch |
|---|---:|---:|---:|
| batch 8 | 30,000 | 240,000 | 8.09 |
| batch 16 | 15,000 | 240,000 | 8.09 |
| batch 16 | 30,000 | 480,000 | 16.18 |

batch 翻倍、step 减半只保持样本量近似相同，更新次数、梯度噪声、Adam 动量与权重衰减累积不等价，收敛效果不保证相同。若按样本量对齐预热预算，1000 步可换算为 500 步，但应视为调参候选，不是自动保证等价；学习率也没有本轮验证过的简单倍增规则。启用梯度累积还需要实现、损失缩放和更新频率核对，当前未启用。

实用顺序：复现先沿用官方 batch/step；再测试显存与稳定吞吐，按数据量设置初始 epoch 预算；通过独立验证轨迹、动作误差及任务结果选择 checkpoint。机器人相邻帧相关性强，应按完整 episode 划分验证集，避免相邻帧泄漏。训练 loss、完成动作预算和超声扫描质量是不同指标。

数据集总帧数主要影响 epoch、步数和总耗时，在每个输入形状相同的条件下通常不会直接增加单步 GPU 显存。

## 6. 为什么 batch 更大不一定更快

应比较样本/秒，而不只比较秒/步。较大 batch 的单步通常更慢，只有速度增长小于 batch 增幅时，吞吐才提高。

| 6000D 实测 | batch 8 | batch 16 |
|---|---:|---:|
| 稳定单步耗时 | 0.715 秒 | 1.468 秒 |
| 吞吐 | 11.19 样本/秒 | 10.90 样本/秒 |
| 对应相同 24 万样本的纯循环估算 | 5.96 小时 | 6.12 小时 |

bs8 稳定统计区间为 step 210→988，bs16 为 30→116；排除首次编译与末次保存。日志频率分别为每 100 和 10 步，且测试时长不同，因此 2.6% 左右差异只支持“没有观察到提速”，不能视为严格性能排名。首次编译、数据准备、checkpoint 保存和速度波动要另计入总时间。

这次没有必要为用满显存增加 batch。更大 batch 的潜在优化效果没有系统比较，短测 loss 不能作为优劣依据。

## 7. 与之前 E-07 的时间、显存如何比较

E-07 用 27,312 帧、batch 32、10,000 步，累计 32 万样本，约 11.72 epoch；完成总耗时 10:39:51，循环耗时 10:37:36，含保存等开销约 3.8256 秒/步、8.36 样本/秒。本次计划 batch 8、30,000 步只有 24 万样本，比 E-07 少 25%；按当前吞吐外推约 6 小时，但正式任务已经停止，没有完成实测总耗时。

总时间差来自样本预算和吞吐两个因素，不能主要归因于 GPU 型号。两次模型、batch、数据、硬件和计时范围均不相同。只有同配置同口径对照才能分离 GPU 的贡献。

E-07 历史 batch 32 测试的 `peak_bytes_in_use` 约 21.44 GiB，不能标为其正式 10k 训练的全程峰值；正式运行 0.95 预分配比例也不是峰值测量。历史 GPU 记为 RTX 4090、49,140 MiB，型号/容量组合未重新核实。不能把 E-07 21.44 GiB 与本次较小 batch 的峰值之差归因于模型更耗显存；参数较少但 batch 更大，仍可能用更多中间缓冲。

## 8. 6000D 与 5090 的判断边界

6000D 已实际完成 batch 8/16 短测；5090 尚未测试。本次“实际缓冲峰值约 16.9/18.2 GiB”表明 32 GB 卡有适配空间，但还需在目标卡核对环境兼容、池分配、初始化/保存峰值和稳定吞吐，不能据此保证完整训练一定成功或推算速度。

早先据 nvidia-smi 32.6 GiB 断言 5090 装不下 batch 8 的判断已订正。显存容量决定能否承载，实际吞吐决定是否划算；型号或显存大小本身不能证明训练更快。

## 9. 当前可确认的结论

US-VLA 完成资源与兼容性准备、batch 8 的 10 步短测、batch 16 的 120 步吞吐测试，以及两组 5 步内存剖析。正式 30,000 步任务只运行到最后日志进度 988 后停止，未到首次保存节点，无可恢复正式 checkpoint；独立 batch 16 测试有 checkpoint。没有完成训练收敛、独立评估或论文指标复现，5090 是待验证项。
