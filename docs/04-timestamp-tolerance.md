# 04 · 时间戳精度：被 float32 吃掉的容差

## 现象

数据集本身没问题，但读视频时偶发解码失败，报「找不到落在这个时间戳上的帧」。
诡异的是：**只在长时间戳上失败，短回合完全正常**。

## 根因

LeRobot 的 `decode_video_frames_pyav` 里有这么一行：

```python
timestamps = torch.tensor(timestamps)      # float64 → float32
```

`timestamps` 本身是 float64 算出来的，进 `torch.tensor` 时被**降级成 float32**。
float32 在 t≈1277s 处的 ULP（最小可分辨间隔）是：

| 时间戳 | float32 ULP | 默认 `tolerance_s = 1e-4` |
|---|---|---|
| 1277 s | 1.22e-4 | **已经超过** |
| 3270 s | 2.44e-4 | 超过 2.4 倍 |

也就是说：数据集跑得越久，时间戳越靠后，float32 能表示的间隔就越粗。
当 ULP 超过解码器用来匹配帧的容差时，就匹配不上了。

**这是个随数据集时长恶化的定时炸弹**——短的测试集上永远不会复现。

## 解决

训练/推理时把容差放宽到 1e-3：

```bash
--tolerance_s=1e-3
```

在 `run_train_smolvla_scan.sh` 里已经写死并附了上面这段理由。

1e-3 在 15 FPS 下对应的帧间隔是 66.7ms，远大于任何真实的时间戳抖动，
同时远小于一帧的时长，所以**不会造成错帧匹配**，只是让比较不至于被
float32 的表示精度卡住。

## 教训

1. 一个只在「长数据」上出现的 bug，在短的验证集上查一辈子也查不出来。
   **验证集要覆盖真实数据的时长范围**，否则「我本地跑通了」是假的安全感。
2. 看到 `torch.tensor(python_float)` 这种写法要警觉：
   torch 默认的浮点 dtype 是 float32，而 numpy/python 侧通常是 float64。
   这类静默降级在数值敏感的地方（时间戳、角度、坐标）都会咬人。
3. 修的时候优先选「扩大容差」而不是「改上游 dtype」：
   后者要动库代码，且会让本地行为偏离官方，以后对不上账。
