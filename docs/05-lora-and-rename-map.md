# 05 · 两处静默失败：LoRA 加载与 rename_map

> 代码：`pi0_ultrasound_lora/serve.py`

这两件事的共同点是：**它们都不报错。**

---

## A. `from_pretrained` 对 LoRA checkpoint 会静默返回随机权重

### 现象

训练完成了，checkpoint 也在。用 `serve.py` 加载它，
**没有抛任何异常**——但策略输出的动作是乱的，跟训练时的 loss 完全对不上。

### 根因

我们用 LoRA 微调（PEFT），所以保存出来的
`checkpoints/012250/pretrained_model/` 目录里**只有 `adapter_model.safetensors`**，
没有完整的 `model.safetensors`。

而 `PI0Policy.from_pretrained(<该目录>)` 的加载路径**没有覆盖 PEFT 分支**：
它没找到自己期待的文件，于是按配置**构造了一个模型并返回**——
权重是随机初始化的。不抛异常，也不打警告。

这是最难查的一类 bug：调用成功、返回了一个模型、类型也对，
**唯一的问题是里面的数字是随机的。**

### 解决：`load_policy_checked`

`serve.py` 里的 `load_policy_checked` 复刻了官方
`lerobot/common/policies/factory.py:565` 的 PEFT 分支，
走正确的适配器加载路径。

### 加一道主动防线

光复刻分支还不够——如果上游哪天改了行为，
我们同样会静默地拿到随机权重。所以加载后**主动检查所有 `lora_B` 的范数**：

```python
# LoRA 初始化时 A 随机、B 全零，所以 B 的范数理应为 0 只出现在「未训练」的情况。
# 真正加载了适配器之后，B 一定已经被训练出非零值。
if 所有 lora_B 的范数都为 0:
    硬失败
```

**全零 = 适配器根本没进来。** 与其让一个随机策略跑在真机上，不如直接崩掉。

### 教训

1. **「没有报错」不等于「加载成功」。** `from_pretrained` 这类 API 的名字暗示了
   它会加载权重，但它的契约里并不包含「加载失败必须报错」。
   涉及权重的加载，要在加载后**主动验证内容**，而不是相信返回值。
2. 检查方式要选「初始状态就不满足」的量。LoRA 的 B 矩阵初始化就是全零，
   所以「B 仍然全零」天然是一个可靠的失败信号——
   **挑校验量的时候，想想它在「成功」和「失败」两种情况下分别长什么样。**
3. 这个 bug 值得提给上游，但还没提。

## B. `rename_map` 覆盖：它在预处理之后才生效

### 现象

客户端发来的观测键名和策略期望的不一样（比如客户端用 `camera`，
策略要 `observation.images.rgb`）。想用 `rename_map` 做映射，
结果报错说找不到键——**映射看起来根本没生效**。

### 根因

`lerobot/async_inference/helpers.py:166` 在**预处理之前**就用客户端给的键
去索引策略的图像特征：

```python
policy_image_features[key]     # ← key 来自客户端观测，此时 rename_map 还没作用
```

也就是说：**传进来的键名必须是「策略自己的键名」**，
`rename_map` 在这个位置救不了你。

（我们的 `remote/README.md` 里把这条写成了硬性要求：
客户端的 camera key 必须直接用策略的键名。）

### 解决

`serve.py` 原本会**无条件**用客户端的 `rename_map` 覆盖服务端的配置。
改成了：**只有客户端显式发了 `rename_map` 才覆盖**，
没发就保留服务端配置。

### 教训

做重命名/映射这类功能时，**它的作用位置比直觉上更靠后**——
在数据管线里，映射通常只覆盖「真正送进模型之前」的那一小段，
而管线前面那些「用键名去查表」的步骤（找相机特征、查 stats、拼 batch）
早就已经按原键名走完了。**排查映射不生效时，先找管线里最早用到键名的那个位置。**
