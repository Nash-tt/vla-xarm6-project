# 推理服务、传输与机器人执行

核对日期：2026-10-13。实现基线：`e8d95cc`。以下行为依据当前代码；历史实测另行注明。

## 1. 推理服务与网络传输

GPU 侧 `pi0_ultrasound_lora/serve.py` 继承 LeRobot 策略服务，主要补充两项行为：

- 检测 LoRA checkpoint，先加载原始底座，再使用 PEFT 加载适配器；检查模型中是否存在 `lora_B` 参数及是否全部为零。
- 客户端没有提供 `rename_map` 时，保留 checkpoint 中的映射配置，避免被空配置覆盖。

`lora_B` 非零检查能够发现缺失或未更新的适配器，但不能单独证明底座、版本和全部权重均正确，仍需记录底座 revision 并进行推理对照。

模型在客户端调用 `SendPolicyInstructions` 后加载。`serve.py --ckpt` 启动时仅检查路径存在，真正加载使用客户端策略指令中的路径；因此服务端启动日志和端口可连接不能证明权重已成功加载。

工控机传输层为 `pi0_ultrasound_lora/remote/remote_client.py`。它通过 gRPC 发送带时间和步号的观测，接收动作块。两个生成的 proto 文件和传输对象定义需与服务端兼容。发送线程、接收线程及动作队列分别管理观测请求、网络接收和执行。当前握手策略类型固定为 π0，部署其他模型需先修改接口并测试。

当前路径在发送侧将两路图像缩为 224×224；主要传输体积下降来自图像尺寸缩小。gzip 为可选压缩。服务端的 `--wire numpy/torch` 控制下行动作的数据类型，不控制上行图像尺寸。

当需要强制新观测入队时，客户端设置 `must_go`；服务端据此跳过相关合理性检查。它不是周期心跳。重叠动作按 `latest_only` 处理，同一时间步采用新块中的结果，已执行的旧时间步被过滤。当前未进行时间集成，即没有将多个预测按权重合成为单个动作。

## 2. 真机客户端与执行约束

`robot/real_robot/real_robot_client.py` 继承传输客户端，增加 RealSense、实时超声和 xArm 状态读取，以及动作检查和运动接口。默认影子模式仅记录策略输出；运动执行需要显式执行参数与确认字符串。`--validate-only` 用于本地依赖和配置检查，不连接设备。

每次下发前检查连接、控制器错误与警告、状态、力与力矩、跟踪误差及动作跳变。示教轨迹约束仅在提供 `--safety-trajectory` 时生效。可选速率限制器将远处目标变为逐步逼近的位姿；默认不开启。

| 检查项 | 当前默认值 | 适用范围 |
|---|---|---|
| 力 / 力矩上限 | 40 N / 5 Nm | 每次下发前检查 |
| 单步位置 / 姿态变化 | 3 mm / 2° | 相邻目标 |
| 跟踪误差 | 12 mm / 5° | 目标与实际 TCP |
| 轨迹管 | 15 mm / 8° | 必须提供安全轨迹 |
| 图像最大年龄 | 0.5 s | RealSense 与超声 |
| xArm 状态最大年龄 | 0.25 s | `snapshot()` 默认值，不受图像参数控制 |
| 单次运行时间 | 10 s | 控制循环 |
| 动作队列空超时 | 0，关闭 | 需显式配置才能启用 |

这些数值是代码默认配置，不代表已完成接触扫描场景的安全验证。空队列时程序不重放旧动作，但网络连接存活、发送接收均未报错时，仍可能长期没有新动作，因此不能把空队列超时关闭解释为不存在停供风险。

## 3. 启动与控制时序

客户端依次建立通道、发送策略配置、启动接收及发送线程、请求初始观测，等待第一组动作后开始固定频率执行。回放入口默认额外预热两个动作块；真机入口的初始等待时间默认 180 s，与回放入口 120 s 不同。

观测发送采用容量为 1 的队列。已有观测等待发送时，不积累大量旧观测；发送线程执行 RPC，控制循环继续按固定频率消费动作。动作队列量低于 `chunk-size-threshold` 比例时请求补充，默认阈值 0.9。阈值影响请求时机，不是运动安全阈值。

发送和接收线程的错误写入 `observation_error` 与 `rx_error`，主循环据此退出。gRPC 通道本身配置了部分错误的重试；最终传播到主循环的错误不会由控制逻辑无限重试。

控制环使用单调时钟计算下一期限，运行落后时重置期限，避免持续追赶。Python 线程调度、网络和设备回调都可能产生抖动，实际执行频率需要测量。

## 4. 原始目标、限速命令与执行日志

日志分别保存模型原始目标 `raw_policy_target`、接受检查的目标 `commanded_tcp_pose`，以及 `rate_limit` 结果。默认路径两者相同；开启限速后，本机逐步逼近远处绝对目标，平移与姿态分别按速度上限计算每周期步长。限速路径会折返角度；默认直接目标路径没有统一角度折返。

影子模式记录 `shadow_valid` 与拒绝原因，主要验证几何约束；执行模式才要求力信号有效并进行对应检查。影子测试通过不代表全部执行条件通过，特别是力信号、起始位姿和 SDK 运动返回码。

执行准备会改变使能、模式和状态，但没有自动移动到扫描起点。异常或中断在已执行状态下进入停止状态，不自动清除错误。实际停止与恢复步骤应按设备测试记录核实。

## 5. 验证次序

先验证 checkpoint 的加载与离线输出，再使用数据回放检查网络对象、时序和误差，最后接入实时观测开展影子测试。只有完成相应设备与影子检查后，才安排有界运动实验。本次文档重建没有执行运动测试。

完整操作和验证命令见 [环境与操作指南](06-环境与操作指南.md)。每次部署记录服务端和客户端 commit、checkpoint、图像处理、超声配置、队列参数及日志位置。
